# M2: HTTP target adapter, stand-in server and first private run

Read `AGENTS.md`, `docs/spec.md`, the ADRs (including ADR 0008) and the descriptions of PRs #2, #4,
#5 (M1.2) and #13 (M1.5) first. One pull request against `main`.

## Goal

The harness can attack an API target from the outside: log in, plant fixtures, chat over a streamed
response, map the stream to an `Observation`, deny approvals and clean up. The code is public and
generic, tested against a local stand-in server. David writes the private config and item set and does
the first private run against his red-team instance. Scope: `direct` and `indirect_doc` items only.

## Prerequisites (David, not the agent)

1. A **red-team instance** of the private target: its own compose project (own database, vector store
   and identity provider), never the instance that holds David's real knowledge base. No coding-agent
   sessions run against it.
2. An identity-provider client that exists **only in the red-team instance** and allows password
   login for test users. Because the real instance lacks it, the harness can't log in there by mistake.
3. `private/targets/<name>.toml` and `private/sets/<name>.jsonl` (+ fixtures), written by David with
   the planning chat. Agents never read them.

## Deliverables

1. **HTTP target adapter** (`src/pecker_drum/targets/http/`), configured by a TOML file (Pydantic
   schema, unknown keys rejected):
   - `base_url`, timeouts, `label` (used as the model slug in report names).
   - `auth`: `oidc_password` with `token_url`, `client_id`, and a `users` map from `item.user.sub` to a
     username plus the **name** of the env var holding the password. Refresh before expiry. Config
     files name env vars; they never contain secret values. Passwords come from the shell
     environment only: the `.env` rule of ADR 0007/0008 stays as it is (only the OpenRouter names).
   - `chat`: request to create a conversation, request to send a message, a server-sent-events stream.
   - `events`: mapping from event name or `type` field to channel (answer tokens, sources, tool call,
     tool result, approval required, error, done) with simple dotted field paths.
   - `approvals`: the deny request.
   - `fixtures`: document upload (multipart), status polling (list endpoint, id and status fields,
     terminal values, timeout), delete; conversation delete.
   - Templates are plain `{conversation_id}`-style substitution. No `eval`, no template engine.
2. **Observed channels:** `Observation.observed` lists the channels the target exposes. If no success
   or contained predicate fired and an item's predicate needs an unobserved channel, the outcome is
   `unobservable`: excluded from rates like `error`, listed per item, and shown in the report header.
   The advisory judge (ADR 0008) does not label `unobservable` attempts.
3. **Fixture lifecycle per attempt:** plant, wait until indexed, ask, deny approvals, then clean up
   documents and conversation in a `finally`. Planted documents carry the tag `drum-fixture-<run id>`
   in their title. `drum cleanup --target … --run-id …` removes leftovers; every run ends by listing
   documents and fails loudly if a tagged one remains. Concurrency is 1 for targets with fixtures.
4. **Stand-in server** for tests and `--target stub`: binds `127.0.0.1` on a random port, speaks the
   API shape of `docs/examples/http-target.toml` (token endpoint, conversations, streamed messages,
   document upload/status/delete, approvals) and has obedient and safe modes driven by `self_test`,
   like the fake models. The example config and the stub use generic names only, nothing from a
   private target.
5. **Item scope filter:** `--vectors direct,indirect_doc`; items outside the filter are skipped and
   listed in the report.
6. **Safety caps:** requests per minute, request timeout, maximum wall time, maximum attempts, abort
   after N consecutive errors. Ctrl-C triggers cleanup. The run id includes a config digest computed
   without secret values (and the judge id when a judge is set, as in M1.5).
7. **Reports and run records** for private HTTP targets go to `private/reports/` by default, run
   records to `private/reports/.runs/`, because both hold the target's full answers. The
   stand-in's data is public, so its reports go to `reports/`. `drum report --run-id` reads
   `reports/` by default and `private/reports/` only with an explicit `--reports-dir
   private/reports`, which the gate blocks for agents (amended in the PR #16 review, David's
   decision). Report names include the target label. `--judge` works for HTTP targets as for the
   twin.
8. **Docs:** README section "Attack your own API target" (bash and fish; passwords via `read -s` /
   `read -s -x`), spec updates, an ADR for the adapter design and the `unobservable` outcome.

## Acceptance checks

- [ ] Lint, format check, Pyright and tests pass; tests make no network calls beyond `127.0.0.1`.
- [ ] `drum run --target stub --set public_v1 --vectors direct,indirect_doc` with the obedient and the
      safe stand-in mode gives the same outcomes for those items as the twin self-tests, with and
      without `--judge fake:reported`.
- [ ] Tests for: token refresh; stream parsing (split chunks, multi-line data, unknown events ignored,
      malformed data → `error`); approval deny; polling timeout; cleanup after an exception and after a
      simulated Ctrl-C; leftover detection; the `unobservable` outcome.
- [ ] A test proves a known test password never appears in logs, reports, run records, checkpoints or
      run ids.
- [ ] A test proves that a stub run without `--reports-dir` writes its reports and run record under
      `reports/` (in a temporary working directory), not under `private/reports/`, and that
      `drum report --run-id` reads `private/reports/` only with `--reports-dir private/reports`
      (amended in the PR #16 review).
- [ ] First private run, by David at the end: private set, red-team instance, `--repeats 5`, with an
      OpenRouter judge if David chooses. The report stays in `private/`; the PR gets only the numbers
      David chooses to share.
